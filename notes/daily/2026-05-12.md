### 1. Bug crítico de Duplicar — detectado y fixeado (commit 28a6d69)

**Trigger**: durante testing manual del Listado post-cierre, click "📋 Duplicar" en la propuesta Gamboa tiró:

````
Error al duplicar: Block #0: proposal_id (58a8a7e1-...) no matchea con Proposal.id (3aefb08a-...)
````

**Root cause**: en `_render_proposal_row_actions()` (columna Duplicar), el código seteaba `duplicate["id"]=""` esperando que `save_proposal()` asignara UUID nuevo. Pero los blocks copiados seguían apuntando al `proposal_id` ORIGINAL. `_validate_proposal()` (en `core/proposal_persistence.py`) rechazaba con FK mismatch ANTES de que el primer save persistiera. El "fix" post-save de proposal_id en blocks nunca se ejecutaba porque `save_proposal` ya tiraba ValueError.

**Fix aplicado**: generar `new_proposal_id` ANTES del save, asignarlo simultáneamente a `duplicate["id"]` Y a cada `block["proposal_id"]` en una sola pasada. Un solo save_proposal (antes había double-save fallido).

**Mejora colateral**: separar try/except — `ValueError` (validación schema) tiene mensaje específico, separado de `Exception` genérica.

**Validación**:
- Smoke test stand-alone: original `f6797022` → copia `73dcf7d0`, ambos con FK consistency correcta, 18 blocks preservados
- Smoke test visual: Gamboa duplicada exitosamente como "Gamboa (copia)" con id `8e0adde0`, original mantiene `58a8a7e1`. Banner verde + rerun OK

**Lección aprendida**: el patrón "guardar primero, arreglar FK después" no funciona con validadores estrictos. Hay que generar el ID padre ANTES del save y propagarlo consistentemente.
